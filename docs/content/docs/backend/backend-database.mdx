# 数据库结构

VOZEB PRO 商业版默认使用 PostgreSQL 作为主库。数据库初始化 SQL 由 `web/src/lib/server/database/schema.ts` 维护，服务端统一通过 `web/src/lib/server/database/` 下的 Repository 访问主库。

## 环境变量

```bash
VOZEB_PRO_DATABASE_PROVIDER=postgres
DATABASE_URL=postgres://vozeb_pro:change-me@localhost:5432/vozeb_pro
VOZEB_PRO_DATABASE_POOL_MAX=10
VOZEB_PRO_DATABASE_SSL=0
VOZEB_PRO_ENCRYPTION_KEY=64位十六进制或32字节Base64密钥
```

首次部署后访问 `/install`。状态 GET 只读检查 `DATABASE_URL`、PostgreSQL 连接、表结构和管理员数量，不执行 DDL；表结构由安装页 POST 初始化操作显式创建。有效的 32 字节加密密钥是初始化和创建首个管理员的前置条件。

如果只需要本地文件存储体验，可显式配置：

```bash
VOZEB_PRO_DATABASE_PROVIDER=file
```

## 表名前缀

VOZEB PRO 的 PostgreSQL 真实表名统一使用项目名前缀 `vozeb_pro_`。业务代码里仍然使用逻辑表名，例如 `users`、`billing_orders`、`generation_logs`；数据库执行层会统一映射为真实表名：

- `users` -> `vozeb_pro_users`
- `billing_orders` -> `vozeb_pro_billing_orders`
- `generation_logs` -> `vozeb_pro_generation_logs`

这样同一个 PostgreSQL 数据库里即使存在其他业务表，也能清楚区分 VOZEB PRO 的数据。Schema 中的显式索引和会生成索引的命名唯一约束也必须使用 `vozeb_pro_` 前缀，避免与同一 `public` Schema 的其他应用对象重名。无前缀表不会被自动删除；当前部署和后续读写只使用 `vozeb_pro_` 前缀表。

## 核心表

- `vozeb_pro_image_enhancement_jobs`：独立于原生生图成功状态的持久增强任务，以 `user_id + image_task_id + result_id` 唯一绑定原件版本。`status/phase/next_poll_at/lease_token/lease_until` 支持有界到期领取、行锁跳过争用与旧执行租约校验；`payload` 保存冻结原件、目标和模型连接引用、远端幂等键与任务、尝试事件、永久AI／交付件及固定接收确认身份，不保存端点或Token。原图成功写入与增强入队在同一PG事务，发布关联资产读取／登记复用同一executor；完整媒体保存并回读校验后发布，收据丢失保持成功而只恢复确认。本人读取按任务及用户定向查询，调度只查询到期行。文件Provider使用 `image-enhancement-jobs.json`：原任务锁内先保存意图，执行前核原生成功及冻结原件；发布先creative再enhancement锁，复用锁内快照、先保存creative再写job，跨文件中断沿稳定child身份恢复。该表的实际媒体／GPU及前台接入仍按M5逐项验收。

  普通成功图片的任务结果与创作资产metadata保留公开resultId、enhancementId、nativeSource或enhancementSkip；后者仅含skipped及已知原因。普通4K关闭策略仍有原件事实和独立skipped job，其他无job分支不伪造原件事实。重复登记使用同一来源任务及任务内压缩序号，增强件为独立child，不能覆盖原assetId。增强payload的timings分别保存Worker排队、当前attempt引擎执行及实际交付编码事实；成功Worker快照替换旧Worker计时，独立保留Web编码计时，查询失败不抹除已存事实。只读响应不从轮询间隔推算耗时，未测量字段保持缺失。

  日志候选在既有`generation_log_assets`增加`enhancement_metadata JSONB NOT NULL DEFAULT '{}'::jsonb`，只保存上述四项公开原结果字段；在线定向查询、写入返回与管理员备份均重建相同嵌套白名单。相同媒体URL的不同resultId分别保存，已登记永久媒体不重复下载。管理员响应的`assets[].enhancement`是只对本页按owner/id/resultId/原任务核对后附加的当前摘要，不写回日志或触发Worker；聚合日志按成功slot的assetIndex与taskId关联，缺失时不回退其他任务。持久化与只读关联已通过真实隔离数据库回读，详情刷新／原图下载已有桌面证据；实际业务Route及GPU贯穿仍按M5整体验收，不把模块证据称完整闭环。

- `vozeb_pro_image_enhancement_settings`：管理员高清增强的单例配置，`id='default'`，`value` JSONB 保存默认关闭的启用意图、执行修订号、连接档案、请求超时、鉴权能力模型目录和属于该修订号的检测结果。连接档案的 Token 复用服务端 AES-GCM 加密；管理接口只返回 `hasToken/hasCa`，不回传密钥、密文或 CA 正文。配置修改使用行锁事务，旧修订和迟到检测不能覆盖新配置。旧档案保留以维持已冻结任务的端点/服务归属，凭据通过受控档案引用解析；同服务凭据轮换不改写任务快照。文件 Provider 使用 `image-enhancement-settings.json` 与既有文件锁、原子写入，不把配置放入浏览器存储。

高清增强单例配置的 `value.tta` 保存独立于模型选择的精细增强意图，默认 `false`；缺失时读取为 `false`，无需表结构迁移。配置修订变化只影响新任务；冻结连接的 `model.tta`、远端计划 `engine.tta` 及策略/计划摘要绑定实际模式，恢复不读取新默认替换旧模式。能力目录的 `ttaModes` 与模型默认 `tta` 分开，管理员日志只展示任务冻结模式和已有执行计时。

持久远端计划的可选 `requestTta` 另行冻结请求字段值与存在性，不参与引擎策略摘要；旧计划缺失时继续省略请求字段。Worker 能力升级不得改变同一幂等键的请求正文，丢回包恢复必须复用已接受的原任务。

增强任务 JSON 的 `staged.delivered` 与 `publication.delivered` 保存最终实际格式 `png|jpeg`、地址、尺寸、字节数和摘要；新增无保护全局交付为 JPEG，受保护交付与旧暂存 PNG 保持原格式。远端 `remoteResult` 及完整 AI 结果仍严格 PNG，回执绑定该远端结果；无需表迁移，不覆盖历史文件。

M7 在既有图片任务 JSON 中增加创建时冻结的 `enhancementDelivery`（`ecommerce-delivery.v2`）：明确全局整图或 `product_background`，后者保存商品锚点/源尺寸、规范方向色彩、源/规范源摘要及可信 inline PNG 蒙版/摘要。结果的 `productEnhancementEvidence`（`product-baseline.v2`）分别绑定真实 provider native 与合格原图及其合成证据，不覆盖 `nativeSource`。增强任务 payload 的 `decision.delivery` 固定该合同和合格原图身份，`requestedTarget` 保留请求目标；严格商品背景的实际 target 保持源画幅。`staged/publication.protection` 保存规范版本、源/AI/蒙版/final 摘要、锚点、尺寸及保护像素计数，发布时重建验证。无需新增表或迁移；公开读取只返回范围和技术事实白名单，不返回蒙版或连接凭据。

M8 沿用同一 JSON 结构增加 `scope: local_edit` 与 `scene-enhancement.v1` 保护证据，仅在新建显式4K且已有确认有效局部选区时冻结源、坐标及可信蒙版。合同中的 baseline 是编辑前参考，`decision.delivery.baseline` 是原局部编辑技术通过后的合格原图；`decision.source` 继续保存真实 provider native，三者不能互换。raw native 与合格 baseline 可按既有 `uniform_scale` / `pixel_grid_scale` 规则具有不同尺寸，原 native 技术要求不变。Worker prepare 与 submit 同用冻结的合格原图上下文，下载校验沿相同冻结输入尺寸与模型倍率；最终交付保持源画幅，仅在 `alpha < 255` 允许域写回，alpha255保护区RGBA零差。`requestedTarget` 独立保存请求尺寸，不由4K画质反推更大尺寸；例如精确源画幅1254²时，请求可1254²、推理5016²、交付1254²，不能标为整图4K。`staged/publication.protection` 分别保存完整 AI 与最终件摘要、映射、允许/保护像素数及区域外零变化计数；发布时从原参考和 native 重建合格原图，再用保存的完整 AI 重建最终件，并核staged字节。增强资产保留独立父链，继续编辑需重新确认选区；无需新表、迁移或 Worker 协议升级。当前入口只签发可信二值矩形，空/全域不冻结局部合同，helper软混合不代表画笔UI。旧任务不补签新合同，增强失败不撤回合格原图；本期不新增整图4K导出入口。

上述M8持久合同已有真实 `/create` 受控HTTP整链验证：冻结baseline上传、完整AI/final永久件、receipt及显式final继续编辑父链保持，1254²最终件的1,509,766个保护像素RGBA零差。本期技术独审、固定检查/构建及开发Web/生成Worker同镜像发布已完成，运行构建源为`6e096d2`，发布后PG schema/加密与新Worker心跳正常；后续状态文稿提交不改变镜像来源。该交付不代表真实GPU照片画质或用户人工验收通过。

媒体引用计数包含`image_enhancement_jobs.payload`中的原件、staged及publication完整AI／交付件，失败或取消后仍保留其引用。PostgreSQL沿现有请求storageKey的一次聚合查询，文件Provider读取同一增强JSON；这只是引用保护，不授予任务或物理产物删除权。

- `vozeb_pro_schema_migrations`：已应用的数据库结构版本。
- `vozeb_pro_app_settings`：站点、注册、邮箱、积分、生成、支付配置、逻辑模型目录、渠道绑定和默认模型等全局设置；`logical_models` JSONB 保存用户可见模型及其能力、上游模型、渠道、启用状态和优先级，`ecommerce_generation_enabled` 保存管理员控制的正式电商生图编排开关且默认关闭，关闭时部署侧正式模式不能绕过门禁，影子模式只记录观测快照；`generation_cost_control` JSONB 保存管理员配置的单任务、单用户每日和全站每日积分成本上限，三个值为 `0` 时均表示不限制；`data_lifecycle` JSONB 保存四类技术到期清理开关和单类批次大小，不承载对话、支付、审计等长期业务数据的法律保留期限。
- `vozeb_pro_object_storage_settings`：S3 兼容外部存储单例配置，保存启用状态、Endpoint、Region、Bucket、对象前缀、CDN 地址前缀 `cdn_base_url`、path-style 模式及加密后的 Access Key/Secret Key；CDN 地址前缀显式留空时使用源站签名地址。管理接口只返回密钥是否已配置，不回传明文。
- `vozeb_pro_system_model_channels`：系统模型渠道、分别加密保存的 API Key 与渠道生成回调密钥、模型列表和高级配置；后台不保存渠道验证记录。
- `vozeb_pro_entitlement_plans`：商业套餐权益、每日额度、调用限制和功能标记；新用户不再通过套餐获得注册初始积分。
- `vozeb_pro_users`：用户账号、角色、状态、头像存储键、最多 160 字的个人简介、当前套餐、积分余额和密码哈希；`admin_permissions` JSONB 保存管理员的显式职责列表，并由 CHECK 约束保证为数组，普通用户保持空数组。管理员 TOTP MFA 使用 `mfa_secret_ciphertext` 保存 AES-GCM 密文，`mfa_enabled_at` 表示已完成验证并启用，CHECK 约束禁止启用时间存在但密文缺失。公开注册还原子保存当时的服务条款版本/链接、隐私政策版本/链接和同意时间，五个留痕字段必须同时为空或同时存在。管理员代建账号不伪造用户同意记录。公开创作者接口只按用户名返回允许公开的资料字段，不暴露邮箱、内部用户 ID、职责、MFA 密文或协议留痕。
- `vozeb_pro_sessions`：登录会话 token 哈希和过期时间。
- `vozeb_pro_account_deletion_requests`：账号注销申请、用户资料快照、申请状态、管理员处理备注与处理人快照；同一用户同一时间只能存在一条待处理申请，受理不会自动停用账号或删除业务数据。
- `vozeb_pro_rate_limits`：PostgreSQL 多实例共享的接口限流窗口，保存哈希后的业务键、原子请求计数和重置时间；数据库不可用时服务端临时退回进程内保护。
- `vozeb_pro_email_codes`：注册、换绑邮箱、找回密码验证码及失败尝试次数。
- `vozeb_pro_quota_usage`：按用户、日期和生成能力保存每日积分与次数占用；套餐关闭但生成成本保护启用时仍会写入，以便按用户和全站聚合实际积分成本，退款会原子回退对应日期的占用。
- `vozeb_pro_point_records`：积分流水；非空幂等键全局唯一，AI 消费同时保存服务端请求指纹，用于拒绝同一业务身份对应不同模型、渠道、调用类型或请求参数的重放。
- `vozeb_pro_billing_products`：可售卖套餐商品，分别记录一次性永久积分、套餐有效期内每日赠送积分、价格、生效周期和上下架状态。
- `vozeb_pro_promotion_campaigns` / `vozeb_pro_promotion_products`：限时促销活动及商品活动价；有效区间使用 `[starts_at, ends_at)`，活动价必须低于商品日常价，同一商品的启用活动不得时间重叠。
- `vozeb_pro_coupon_templates` / `vozeb_pro_coupon_template_products`：固定金额或比例优惠券模板及适用商品，保存门槛、封顶、是否叠加活动、领取开关、发行总量、每用户限领、有效期和发行/核销计数。
- `vozeb_pro_user_coupons`：用户持有的优惠券，状态为 `available/locked/redeemed/expired/revoked`；下单时按订单锁定，取消或超时时原子释放，支付成功后核销。
- `vozeb_pro_coupon_redemptions`：订单优惠券核销凭证，每个订单最多一条；整单退款将核销标记为 `refunded`，不自动返券，避免退款套利。
- `vozeb_pro_referral_programs`：单例邀请计划设置，保存功能开关、首单实付门槛、冷静期、邀请人积分、新用户积分或优惠券、月度/活动上限和自动冻结策略。
- `vozeb_pro_referral_codes`：每个用户唯一的稳定邀请码；新邀请码由数据库唯一的公开账号 ID 生成，不再依赖随机碰撞重试。表内只保存聚合点击数和最后访问时间，不保存原始 IP、完整 User-Agent 或设备指纹。
- `vozeb_pro_referral_relationships`：单层邀请关系和归因摘要，受邀用户唯一；保存 HMAC 网络/支付身份风险信号、人工风险状态和处置证据，禁止自邀、重复绑定和两层循环邀请。
- `vozeb_pro_referral_rewards`：首笔有效实付订单生成的邀请人/新用户奖励记录，保存待结算、已发放、已撤销、已拒绝和撤销待复核状态，并关联积分流水、优惠券和触发订单。
- `vozeb_pro_billing_orders`：商业订单主表，记录订单号、商品快照、套餐、支付商单号、支付状态和生效信息；日常总价、活动优惠、券优惠、实付金额、活动/用户券关联及 `pricing_snapshot` 均作为权威价格快照保存，支付、退款和对账只读取实付快照。状态包括 `pending/paid/closed/canceled/refunding/refunded`，退款外部调用期间使用 `refunding` 认领状态。过期待支付订单由原子批处理更新为 `closed` 并记录 `close.source=expiration-job`，多实例使用 `FOR UPDATE SKIP LOCKED` 并发执行不会重复关闭或遗留券锁。独立 `created_at` 索引用于后台财务日期窗口聚合；支付商订单号与支付号分别使用 `(provider, provider_order_id)`、`(provider, provider_payment_id)` 定向索引，对账不再模糊搜索订单列表；财务摘要的对账子查询复用同一日期窗口内的支付流水，不重新扫描窗口外流水。
- `vozeb_pro_payment_transactions`：支付流水，记录支付商交易号、支付渠道、金额、状态和原始回调摘要；独立 `created_at` 索引用于支付金额和状态的日期窗口聚合。
- `vozeb_pro_billing_refund_jobs`：整单退款外部调用与本地补偿任务，保存支付商退款身份、真实尝试次数、租约、待处理时间、错误摘要和补偿载荷。每次维护调度只认领并执行一次尝试，后续节奏由外部维护调度决定；表内不设置固定最大尝试次数或指数退避。
- `vozeb_pro_billing_reconciliation_runs`：支付商账单导入对账批次，保存渠道、来源、导入人、文件名、行数、匹配数、异常数和金额差额摘要。
- `vozeb_pro_billing_reconciliation_rows`：支付商账单对账明细，保存规范化后的订单号、支付商流水号、金额、币种、状态、本地匹配订单和差异代码；不保存整份原始 CSV。
- `vozeb_pro_user_plan_assignments`：用户套餐生效记录，用于保存由订单、CDK、管理员或系统发放产生的套餐权益周期。
- `vozeb_pro_payment_provider_events`：支付回调事件，用于保存支付商事件 ID、签名校验结果、原始 payload、`processing_at` 认领时间和处理状态，支持重复回调、超时接管和失败释放。
- `vozeb_pro_cdk_codes` / `vozeb_pro_cdk_redemptions`：CDK 和兑换记录。新 CDK 使用同一条记录的完整 UUID 生成稳定密钥，不再预查并执行固定次数的随机碰撞重试；PostgreSQL 后台列表使用数据库侧的关键词、状态筛选、聚合统计和分页，只读取当前页兑换明细，文件 Provider 保持相同业务结果。
- `vozeb_pro_announcements`：站内公告。
- `vozeb_pro_prompts` / `vozeb_pro_prompt_seed_sources`：公共提示词、用户提示词和种子来源。

文本、图片、视频、音频和漫剧整集合成终态更新使用带 `user_id + task_type + allowed status` 条件的原子 `UPDATE`；任务尝试元数据通过存储层原子 mutate 合并，避免取消状态被旧快照覆盖。用户取消、后台成功、后台失败和过期检查同时发生时只有一个状态转换能成功，退款由成功抢占终态或检测到已取消结果的一方执行。

## Repository 边界

局部编辑结果在已有 `generation_tasks.payload.result` 保存 `sceneProtectionEvidence`，包括真实 `nativeSize`、`normalization=none|uniform_scale|pixel_grid_scale`、源图/原生/蒙版/合成摘要与稳定媒体地址。同比或共同整数取整适配使用源坐标的 `mappedOutsideChangedPixels`，`nativeOutsideChangedPixels` 仅同尺寸保留；`canvasEvidence` 分别保存原生与最终尺寸和实际适配方式。技术交付与管理员 `ecommerce_trace` 保留 `nativeMatches` 的真实值，使用独立 `mappingVerified` 记录源/native/mask/composite 重建验证结果；不同原生分辨率不伪装为原生 exact 通过。沿用现有 JSONB 字段和媒体登记，不新增表或独立尺寸迁移。

管理员设置新增 `ecommerce_visual_quality_check_enabled BOOLEAN NOT NULL DEFAULT false`，由 `ecommerceVisualQualityCheckEnabled` 开关管理，定向更新和完整设置 upsert 均保留。每轮快照冻结 `qualityPolicy=disabled|advisory`；旧无策略任务保留恢复语义。新任务技术通过先交付，advisory 复用持久 `review_pending` 队列，报告只补建议。

流水总状态记录交付 completed，真实视觉状态独立保留在 quality_check；关闭记 not_run、无模型。reviewAttempts 与任务集合 CAS 防迟到报告覆盖，日志补偿读取同归属 child/冻结 Run，旧 trace CAS 防止补偿降级；不重复调用模型。

用户、Session、邮箱验证码、积分、CDK、公告和设置属于在线实体：PostgreSQL 使用定向 Repository、参数化 SQL 和必要的事务行锁更新，积分消费、失败退款与管理员调整在同一事务内完成用户锁定、每日钱包结算和幂等流水写入。在线功能必须按用户、实体、状态、时间窗、分页或聚合结果查询，不能先加载整张业务表再在应用层筛选；Canvas 交接幂等检查也直接按稳定项目主键读取，不加载用户全部画布 JSON。用户数据导出通过用户范围分页依次收集 Canvas、素材库、媒体登记和其他业务记录；PostgreSQL 下旧的完整 Canvas、素材和用户媒体读取入口会拒绝执行。认证、提示词、生成记录和注销申请的完整快照只保留给管理员备份事务，普通运行时代码不能直接调用。

## 当前接入状态

`web/src/lib/auth/` 通过用户、Session、设置、积分、CDK、邮箱验证码和公告 Repository 读写对应关系表；文件 Provider 保留相同业务接口和进程内串行 mutation。PostgreSQL 在线路径不再把完整 `AuthDatabase` 删除重写。管理员后台业务操作按 `admin_permissions` 与当前 Session 授权，不进行逐次密码/TOTP 复核；系统渠道 API Key 与管理员 MFA Secret 在数据库中只保存密文。MFA 启用或关闭会保留当前 Session 并撤销该管理员的其他 Session，服务器恢复命令会清除 MFA 并撤销全部 Session。常规业务备份不导出 MFA Secret，导入也不能覆盖服务器当前 MFA 状态。

`web/src/lib/prompts/store.ts` 以及 `web/src/lib/server/` 下的生成日志、统一创作运行时、Canvas 项目、素材库、短剧项目和审计日志 Store 已接入 PostgreSQL。对应 JSON Provider 保留为单机文件部署方式。媒体业务记录始终保存稳定站内相对路径，不保存 OSS 源站、CDN 域名或临时签名；读取时按每条媒体登记的 `storage_provider` 选择本地文件，或根据当前 CDN 地址前缀与登记的对象路径动态生成读取地址，CDN 留空时使用短期对象签名地址，不受当前外部存储开关影响。

按用户删除生成日志时，PostgreSQL 使用后台 `data_lifecycle.maintenanceBatchSize` 读取稳定排序批次，在事务内锁定并删除日志，每批提交后再按真实 `storageKey` 重新统计全站引用并清理媒体。管理员永久删除用户前会在同一用户行锁事务内分页锁定并快照该用户媒体登记，避免用户外键级联先删除对象存储定位信息；提交后才使用快照清理本地文件或 S3 对象。订单、邀请奖励、作品发布与治理等受保护商业记录仍遵循各自外键和运营留存规则，不能由媒体快照流程绕过。

作品发布、广场治理和社区互动只在 PostgreSQL Provider 下启用。用户保存草稿、提交审核、编辑驳回稿、下架、重新上架以及管理员通过、驳回、下架都由 `workPublications` Repository 执行所有权校验和事务更新；用户主动下架后只能恢复最近一次已通过且公开可见的版本，管理员下架不能由用户直接恢复。用户或管理员只能在作品下架后永久删除发布主记录、全部版本快照、发布媒体关联、治理案件、通知和点赞，源素材、Canvas/短剧项目及媒体文件保持不变。`workGovernance` 使用稳定游标读取当前 `active + approved + public` 版本，并负责精选、举报、申诉和版本恢复。`workCommunity` 维护点赞、关注、拉黑、互动通知和 7/30 天榜单；只有有效账号、非作者且互动时已注册满 24 小时的点赞进入榜单分数。举报锁定提交时的版本，旧举报不会下架后来上线的新版本。公开媒体每次请求都会重新校验作品、版本和生命周期后再读取本地文件或生成短期对象签名地址。

外部存储开关只决定新媒体写入位置。开启后新上传和新生成媒体只写对象存储，不保留本地持久副本；关闭后新媒体恢复写入 `VOZEB_PRO_DATA_DIR`。后台可把已有本地登记分批迁移到对象存储，迁移候选和过期清理均通过带条件和上限的批次查询读取；只有对象上传和登记更新成功后才删除本地源文件，失败文件保留用于重试。

`billing`、`promotions`、`coupons` 和 `referrals` Repository 已提供套餐商品、限时活动、优惠券模板、用户券、邀请计划/关系/奖励、订单、支付流水、支付回调事件、用户套餐生效记录、核销凭证、支付商账单对账批次和对账明细的基础读写能力。下单事务按稳定顺序锁定商品与用户券，保存日常价、活动优惠、券优惠和实付快照；关闭、超时、支付成功与整单退款沿用同一订单事务更新券状态。受邀用户首笔可信实付订单在支付事务内生成唯一奖励，冷静期到期后由维护接口或后台人工结算；退款和管理员拒绝会撤销未结算奖励、反向积分流水或安全撤销未使用优惠券，已锁定/核销优惠券进入人工复核。后台财务摘要通过一次 PostgreSQL CTE 查询聚合订单、支付、渠道和对账异常；缺少成功支付的已支付订单按订单计数，正常已退款订单不会因保留原成功支付流水而误报。当前已接入套餐商品/促销/优惠券/邀请奖励配置 API、用户领券/报价/创建订单 API、订单列表 API、支付成功后开通套餐/发放积分服务、真实支付下单参数生成、后台账单导入对账，以及 `/api/billing/webhooks/{provider}` 支付回调入口。

后台支付配置已通过 `vozeb_pro_app_settings.payment_config` 保存；Stripe、支付宝、微信支付、PayPly 和人工确认的密钥会按字段加密存储。支付宝在同一个 Provider 配置内保存 `mode=official|face_to_face`，因此官方支付和当面付天然互斥，不会向用户暴露两个支付宝渠道。支付下单、回调验签和后台配置状态读取时优先使用后台保存值，环境变量仍作为服务器部署兜底。

全新 PostgreSQL 初始化后会写入 `free`、`creator`、`pro` 三档权益，并预置 `creator-monthly`、`pro-monthly` 两个可售套餐商品。重复执行 schema 初始化不会重复插入或覆盖运营后台后续修改。

# Agent 任务

创作 Agent Run 复用 `generation_tasks` 持久化，`task_type = agent`，JSON payload 保存会话 ID、Surface、可选项目、用户需求、运行状态和任务计划；事件写入 `creative_run_events`，生成结果登记到 `creative_assets`。图片、视频、音频和文本子任务继续使用现有任务类型，并写入父 Run、会话、项目和尝试次数关联。真实执行状态以后端记录为准，画布节点 metadata 仅承担展示和关联。

规划上下文读取当前会话的持久摘要和最近 12 条已完成消息，更早消息按序写入 `creative_conversations.context_summary`，并用 `context_summary_through_sequence` 防止重复摘要。服务端按 Surface 和实际能力筛选模型、只加入用户显式选择的 Skill，并完整保留这份已验证上下文，不再叠加平台固定字符预算或输出 token 上限。当前 Run 的用户消息和助手占位消息不会重复进入自身规划上下文；真实供应商上下文能力仍需在启用渠道时验收。

任务可保存多份媒体引用。依赖任务完成后，执行器从其稳定 `assetId` 重新读取持久媒体位置并注入下游图片或视频请求；`parent_asset_id` 保存首个父资产，其余父资产 ID 记录在资产 metadata 中。

同一用户的 `client_request_id` 保持唯一。重复提交 Agent Run 时返回原运行，不重复创建用户消息、助手占位消息、子任务或计费。每份并发结果以独立子任务身份合并写回父任务，并追加 `task.child.completed/failed`；已经成功的子任务与资产不会因兄弟失败而丢失。SSE 使用 `creative_run_events.id` 作为 `Last-Event-ID`，只重放游标之后的事件。

Chat 规划可以返回 Canvas 或短剧 `projectHandoff`。服务端使用 `handoff-{runId}` 作为稳定交接 ID，在所有生成任务完成后合并规划引用资产与本轮新资产，写入一次 `project.handoff` 持久事件，并将完整交接信息保存到助手消息 metadata 和 `run.completed`。Canvas 与短剧均通过服务端项目 API 按稳定交接 ID 幂等创建，不把媒体 base64 写入项目或交接记录。

`app_settings.generation_concurrency` JSONB 同时保存 `agent/image/video/audio/text/render` 六类单用户并发上限；Agent 新建、暂停恢复和失败子任务重试读取后台 `agent` 值，漫剧整集合成读取 `render` 值，不使用代码内固定常量。

后台 Agent Skill 保存在 `app_settings.agent_skills` JSONB 字段中，包含名称、用途、执行规则、启用状态和触发关键词。系统默认内置并启用“电商生图”Skill，管理员可在模型渠道设置页修改、停用、删除或新增 Skill。

Skill 还可记录 `sourceUrl`、`sourceVersion` 和 `license`。默认电商生图 Skill 来源为 `buluslan/gpt-image2-ecommerce` v0.1.0（MIT），项目仅适配其工作流与模板匹配规则，不使用其 Codex CLI/Shell 执行链。
