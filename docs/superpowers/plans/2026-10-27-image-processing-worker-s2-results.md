# 图像处理 Worker：S1 接缝修正与 S2 单任务结果

本轮完成大商品原尺寸分割的算法修复与单任务技术验证，关联 [SOP](2026-10-27-image-processing-worker-sop.md)、[固定契约](2026-10-27-image-processing-worker-contracts.md)及[43项测试设计](2026-10-27-image-processing-worker-test-cases.md)。源码修改留在开发分支，尚未部署。正式图像子进程、队列和多副本仍属于 S3 及后续阶段。

## 算法与工作区

实际入口仍是 `buildWhiteBackgroundProductProtection`。现有 service 保留锚点校验、Sharp 解码/编码、区域构造和返回契约；`web/src/lib/image-processing/core.ts` 负责已解码 RGBA 的纯像素分割。

旧实现用普通数组保存全部背景队列、所有前景组件，再创建主体 Set。新实现用一个 Uint8 状态图和一个可复用 Uint32 队列，只保留最大合格组件的 seed/面积/边界及次大合格面积。选定主体后原地将已解码 RGBA 改成蒙版，不再分配第二幅原尺寸 RGBA。

| 同时存活的显式像素存储    | 字节数  |
| ------------------------- | ------- |
| 解码 RGBA，随后复用为蒙版 | `4 × N` |
| 背景/前景/主体状态图      | `N`     |
| 可复用遍历队列            | `4 × N` |
| 合计                      | `9 × N` |

N 为原尺寸像素数。64MP 对应 576,000,000 字节，约 549.3MiB。这个上界只描述显式像素存储，**不是总 RSS 或编解码原生分配的硬上界**。

四连通、边界连通背景、白色/透明阈值、minimumArea 过滤后再按 5% 判断多主体、原尺寸及原有错误类身份均保留。压缩原件字节和调用方分析对象不改写；不通过缩小蒙版降级。

## 失败证据与回归

在无网络、1CPU、1536MiB、禁用 swap 的隔离容器中，测试 fork 的 V8 old-space 保持 384MiB：

- 旧实现的小图控制通过；42.7MP 商品进入实际公开函数后触发 `Reached heap limit / JavaScript heap out of memory`。Vitest 主进程正常收口，cgroup 的 `oom_kill=0`；这是有效产品失败，区别于缺模块或路径错误。
- 相同输入、同一限制下，修复后的 42.7MP 与 64MP 均完成，最终三行小图/42.7MP/64MP 回归全部通过。断言真实文件保存、源 hash、原尺寸、主体边界、四个边界像素和保护 alpha 总和。
- service 与保护区域同轮 71 项通过，包含白/透明 1px 细杆及开放背景通道，以及 minimumArea 与恰好 5% 的阈值回归。
- 调用方、连续编辑、图片编译、选区和 Run 操作七文件另轮 280 项通过。各轮证据分别保留，不累计历史测试数量。
- 视觉准备、模型缩图和生成输出预算三文件另轮64项通过。新增F03/F04使用真实生产视觉准备与文本运行层，向本地模型fixture发送实际HTTP请求；完整解码请求中的图片分别为2048×1536和1536×2048，均不超过4MiB。原JPEG字节/hash、展示方向尺寸和输入对象保持，生成输出默认40MP拒绝测试也通过。

新增源码没有保留测量用临时 console。输入损坏、超 64MP、EXIF 方向、多主体、接触边缘及不可信背景的既有可达路径继续通过相应回归。

## 完整 I/O 测量与候选预算

以下每行使用预先生成的输入和全新 Node 进程，执行“读取压缩原件→完整解码→实际生产像素内核→原尺寸 PNG 编码→文件保存”。夹具构造和保存后验证解码单独记账，不纳入这些峰值。运行镜像为 Node 22.23.4、Sharp 0.35.5；宿主构建/浏览器使用 Node 22.22.2，TypeScript 为 5.9.3。UV 线程池为 2，Sharp concurrency 为 1。

| 输入                     | 压缩字节  | 进程峰值 RSS | cgroup 峰值 | 处理耗时 |
| ------------------------ | --------- | ------------ | ----------- | -------- |
| F01，64×48 PNG           | 222       | 73.8MiB      | 24.8MiB     | 29ms     |
| F02，7997×5334 PNG       | 349,254   | 416.4MiB     | 368.2MiB    | 2.88s    |
| F10，8000×8000 PNG       | 436,295   | 597.7MiB     | 549.7MiB    | 4.23s    |
| F11，8000×8000 噪声 JPEG | 8,348,936 | 562.2MiB     | 519.5MiB    | 7.64s    |

前三行测量不包含 service 返回时的 base64；F11 额外包含现有 data URL 构造、还原及文件保存。公开 service 的另轮完整测试也覆盖该返回契约：42.7MP 与 64MP 在保存阶段的进程高水位分别约 461.3MiB、647.7MiB；测试框架和夹具准备基线仍包含在其中。最终三行测试整个容器峰值约 985.4MiB，还包含准备和验证，不能混作单任务计算峰值。

RSS 与 cgroup 对共享页、页缓存和归属的统计不同，因此并列保存。所有上述成功轮次的 cgroup `oom/oom_kill` 都为 0。矩形 PNG 易压缩；噪声 JPEG 补充了不同编码和压缩率，仍不证明所有合法照片的原生内存最坏值。

后续准入的候选资源模型为：

```text
requiredMemoryBytes = 向上取整到 MiB（120MiB 进程包络
                                     + 20MiB 原件字节预算
                                     + 9 × N 显式像素工作区
                                     + 4 × N 原生/编码预留）
```

120MiB 来自测量前测试进程高水位 122004KiB 向上取整，包含框架/准备余量；20MiB 沿用既有输入字节策略。4N 是额外一幅 RGBA 大小的候选原生/编码预留，结合实测提供余量，不能当作 libvips 对任意输入的保证。按该模型，42.7MP 为 669MiB，64MP 为 934MiB。

完整原始结果及 `single-job-memory.json` 保存在私有阶段证据中，包含输入/产物 hash、各阶段内存、源码身份、版本、配置和失败轮次。**934MiB 尚未写入运行配置**；S3 必须用实际子进程、监督进程及工件链路复核，S5/S6 再验证准入、并发和部署总预算。参考预处理与结果处理没有因本次商品分割测量而自动获得预算验收。

## S1 打包接缝与桌面路径

首次实际 Next 构建揭示：纯 TypeScript 的 `.mts→.mjs` 探针通过，并不能证明 Turbopack 能从 Web 的 `.mjs` 引用找到 `.mts` 源码。该轮类型检查通过，实际构建失败，原证据保留。

最终共享内核使用普通 `.ts`、Web 无扩展引用；NodeNext 独立编译为 ESM `.js`，运行目录明确声明 `type: module`。未来子进程入口仍可使用 `.mts→.mjs`，并随独立产物携带模块声明。不增加 bundler 依赖或全局解析别名。实际 Web 类型检查、Turbopack 生产构建及 Standalone 启动已通过。

Chromium 使用该生产构建和现有 Web/生成 Worker 监督流程，以大商品配小场景完成一次真实页面提交。现有管理员 trace 记录 7997×5334 保护源尺寸及 `(2400,1200,3200,2800)` 主体边界；受控上游仅一次图片创建，结果展示及刷新恢复同一 Run/产物通过。该轮为 setup 1 项加业务 1 项，不调用真实模型或 GPU，不作为照片画质结论。
