## 6. 三个必须先审阅的关键用例展开

### TC-A01：大商品完整保护处理

前置：S1接口已固定，独立子进程和数据目录；F02合成夹具hash固定，参考角色明确；原件字节与预算profile已保存。

操作：

1. 通过实际入口提交F02商品处理，不抽取复制私有函数。
2. 观察完整读取、解码、分割、编码与保存，收集子进程退出和峰值。
3. 读取保存后的原尺寸蒙版，核对上述字面量像素、主体边界和源图hash。

通过：原尺寸蒙版正确、源图不变、退出正常且在已声明总预算内。若进程因导入、路径或测试环境错误退出，修测试入口后重新记录；不能将这类错误当有效缺陷RED。

### TC-Q03：过期执行迟到不能覆盖

前置：真实PostgreSQL、独立任务；通过实际可控执行边界保留A执行身份，使其租约已失效；B取得新的合法执行身份。

操作：

1. 原图片任务分别用不同 Worker、同一 Worker ID 失租重领，核对每次领取的私有执行身份均已更换；创建 context 不能伪造该身份。
2. B仍在执行时，A以旧身份续租及释放，逐字段比对B的完整持久记录；B的合法续租与释放仍成功。
3. 对续租、释放分别持真实锁，让请求在租约有效时开始等待，确认其等待后跨过实际截止，再放锁；过期执行必须被拒绝，完整记录不变。PostgreSQL使用纯 `SELECT FOR UPDATE` 阻塞，不靠改写行触发重检；文件Provider使用真实mutation锁并单独说明测试时钟。
4. B完成并发布其阶段结果后，A再提交原结果，核对当前所有者、结果引用和公开可读产物。

通过：A不能续活过期租约、释放B的租约或改变B的完整记录及结果；B合法执行保持可用，非image任务沿用原契约。结果引用仍指向B；A产物按未引用产物规则处理，不公开为成功结果。租约用例不代替实际结果提交、上游及计费隔离验收，不能只断言“UPDATE含worker_id条件”。
