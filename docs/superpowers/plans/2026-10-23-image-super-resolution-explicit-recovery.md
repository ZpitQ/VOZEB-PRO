# Windows 内网 Worker：启动诊断与失败恢复

Windows GPU Worker 按可信内网管理员维护，支持 HTTP 与 API Token。当前使用方式以本页和 [内网部署精简方案](2026-10-23-image-super-resolution-internal-windows-scope.md) 为准；此前独立证明准备入口已移除，不再要求操作者准备多层证明材料。

## 升级启动失败后恢复健康版本

当上次升级停在启动阶段并记录为未知、服务已停止且存在健康备份时，使用同版脚本目录中的 `Recover-Worker.ps1`。只需五个输入：

```powershell
.\Recover-Worker.ps1 `
  -Receipt '<安装记录路径>' `
  -BackupReceipt '<健康备份记录路径>' `
  -RecoveryRoot '<同卷的新归档目录>' `
  -CredentialFile '<已有凭据文件路径>' `
  -TimeoutSeconds '180'
```

恢复使用原安装锁，核对目标服务、端口和完整备份；在修改前检查当前五个数据目录与健康备份的全部文件内容一致。当前数据已有变化、服务仍运行、端口冲突、备份损坏或数据库不可读时拒绝覆盖，保留现场。该直接入口只支持已有健康前版本的升级启动失败，不是任意数据库损坏的修复命令。

程序自动读取原失败操作和摘要，归档原失败记录与数据，复制备份到独立暂存目录，使用健康旧版本的运行时检查暂存数据库，再恢复数据并启动健康版本。备份保持独立。原十参数证明恢复调用仍兼容，普通内网运维使用上面的五参数入口。

成功返回 `worker_recovery_complete`、`outcome=known` 和新的 `bootId`。结果中的 `qualificationRequired=true` 表示新进程仍需 GPU 自检，不能沿用旧进程的资格。自检通过后再确认能力接口为 `ready=true`。

## 失败时的处理

查看新归档目录中的 `recovery-receipt.json`、`failed-receipt.json` 和阶段记录。复制、交换、启动或清理失败时保留备份、原失败数据及已完成阶段，不自动删除数据库、反向交换或循环重试。

若结果为未知，先查看服务与归档现态，再决定下一次独立维护操作。不要直接重复上次升级、手工改成成功或删除占用信息。当前数据和备份不一致时，应先确认新增任务及数据差异。

## 查看生成准备错误

认证的 `GET /v1/maintenance` 可返回 `runtime.adapter.prepareDiagnostic`，含 `prepareStage`、`nativeStage` 和 `nativeErrorCode`，用于定位准备失败。启动诊断中的 `failureNativeErrorCode` 保存可取得的 Windows 系统错误码。

诊断不替代任务状态。任务仍为未知或占用执行槽时，先核对具体运行状态，避免重复计算。

## 当前验证范围

五参数入口及旧恢复入口定向回归通过，数据保留和失败处理已有本地测试。内部测试机已完成一次真实恢复：健康旧版本启动成功，原十三个任务、七十八份原始记录及十三张原图保留，十二份结果完整下载并通过摘要校验。新进程单次 GPU 自检实际输出 5016×5016 PNG，能力恢复可用。

以上是一次恢复场景的实际结果。完整 M3 还需剩余运行中恢复、维护与卸载验收，以及最终安装包交付；本页不声明整阶段完成。
