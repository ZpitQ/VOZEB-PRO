# 电商商品图生成 SOP 规格

## 目标

为跨境电商家居商品提供一句话图生图体验：用户上传商品主参考图，可选上传场景参考图，再用一句自然语言描述希望得到的结果。系统自动完成图片角色识别、视觉分析、编辑规划、模型路由、生成和商品保真验收。

首个 MVP 固定为：

```text
单张白底商品图 → 单张欧美家居生活方式场景图
```

首期同时支持同一对话中的连续编辑，但不开放商品颜色、材质和结构修改。

## 范围

### 首期包含

- `/create` 统一创作入口。
- 一张商品主参考图。
- 可选一张场景参考图。
- 一句自然语言创作请求。
- `product_to_scene` 商品场景生成。
- `local_edit` 的背景、环境、场景道具、光线和阴影修改。
- 连续编辑：默认继承最近成功结果，支持明确引用历史结果建立编辑分支。
- 原始商品锚点与当前场景基线双基线。
- `strict_product` 商品严格保真策略。
- GPT-5.6、gpt-image-2.5 和 nano banana 2 的逻辑角色路由。
- 生成后的商品核心验收和灰度回退。

### 首期不包含

- Canvas 和短剧入口。
- 多商品组合。
- 海报文字重排。
- 商品颜色、材质、结构或包装文字修改。
- 自动多轮修复。
- 用户手工配置模型、策略、mask 或内部提示词。
- 计费规则改造。

## 用户 SOP

1. 用户上传一张白底商品图。
2. 用户可选上传一张场景参考图。
3. 用户输入一句话，例如“把这个商品放在明亮的现代客厅里”。
4. 系统自动识别上传图片的角色：商品主参考图或场景参考图。
5. 系统识别用户意图并生成内部 `EcommerceEditPlan`。
6. 系统以 `strict_product` 生成结果，保护商品核心区并允许背景和融合光晕区生成。
7. 系统执行商品基线验收。
8. 用户看到一张结果图和简短状态，不看到内部计划、提示词或模型选择。
9. 用户可以继续输入“再亮一点”“把右边的绿植去掉”等一句话，默认基于最近结果继续编辑。

当用户上传新商品图时，系统建立新的原始商品锚点。用户明确引用历史结果时，系统从该结果创建新的编辑分支，不覆盖原结果。

## 领域模型

领域词汇以根目录 [CONTEXT.md](../../../CONTEXT.md) 为准。生成任务必须区分以下概念：

- 商品主参考图：决定商品身份和商品核心像素。
- 场景参考图：决定环境、风格、光线、镜头和构图线索。
- 原始商品锚点：连续编辑链路中永久的商品事实来源。
- 当前场景基线：最近成功结果，用于继承当前场景和已完成的环境变化。
- 商品核心区：轮廓、Logo、包装文字、颜色、比例、材质纹理和主体像素。
- 融合光晕区：边缘、接触阴影、反射、高光和少量环境遮挡的有限区域。
- 场景增量：本轮新增或改变的背景、道具、光线、氛围和构图内容。
- 编辑分支：从明确选中的历史结果创建的新连续编辑链路。

## 核心契约：EcommerceEditPlan

`EcommerceEditPlan` 是用户自然语言、视觉理解、模型路由、图片执行和结果验收之间的唯一内部任务契约。用户原话、内部计划和最终执行 prompt 必须分开保存。

```json
{
  "planVersion": "ecommerce-edit.v1",
  "operation": "product_to_scene",
  "source": {
    "productAnchorId": "asset-product-001",
    "currentSceneBaselineId": null,
    "sceneReferenceIds": ["asset-scene-001"]
  },
  "baseline": {
    "productFacts": {
      "identity": "白色陶瓷台灯",
      "outline": "圆柱灯罩和木质底座",
      "color": "暖白和浅木色",
      "material": "陶瓷、木材",
      "brandText": [],
      "view": "三分之二正面"
    },
    "sceneFacts": {
      "space": "现代客厅",
      "composition": "商品位于画面右侧",
      "lighting": "柔和自然窗光"
    }
  },
  "delta": {
    "requestedChanges": [
      "生成现代客厅环境",
      "加入木质边几和绿植",
      "保留商品正面视角"
    ],
    "targetObjects": ["background", "scene_prop"],
    "targetRegions": ["background", "product_halo"]
  },
  "preserve": {
    "productCore": [
      "outline",
      "brand_text",
      "color",
      "material",
      "scale",
      "view"
    ],
    "sceneElements": []
  },
  "strategy": "strict_product",
  "modelRoles": {
    "visionAnalysis": "logical-vision-model",
    "editPlanning": "logical-planner-model",
    "generation": "logical-image-model",
    "qualityCheck": "logical-vision-model"
  },
  "continuity": {
    "parentResultId": null,
    "branchId": "branch-001"
  },
  "validation": {
    "requiredChecks": [
      "product_identity",
      "product_outline",
      "brand_text",
      "requested_scene_change"
    ]
  }
}
```

契约不允许以下行为：

- 用历史 prompt 文本猜测用户要引用哪张图。
- 用当前后台默认模型覆盖已开始任务的模型快照。
- 将场景参考图误当成第二个主商品。
- 视觉分析失败后静默降级为无参考图生成。
- 把商品核心验收失败当成普通图片生成成功。

## 运行架构

首期保持现有 Next.js 单体部署，在同一项目内建立清晰的内部边界：

```text
/create
  ↓
Agent Run
  ↓
商品素材角色识别
  ↓
vision_analysis
  ↓
edit_planning
  ↓
EcommerceEditPlan 校验
  ↓
provider prompt compiler
  ↓
image task executor
  ↓
商品核心验收
  ↓
公开结果与内部快照
```

逻辑上始终区分 `vision_analysis` 和 `edit_planning`。简单请求可以在物理层合并两次 GPT 调用；商品场景和局部编辑默认使用两阶段，便于验证参考图角色、商品核心和编辑区域。

## 模型路由

模型通过逻辑角色配置，不在业务代码中写死具体模型：

```text
vision_analysis  具备图片输入和结构化输出能力
edit_planning    能理解视觉分析并生成 EditPlan
generation       支持图片生成/编辑和参考图输入
quality_check    能比较原始锚点、当前基线和生成结果
```

每个角色允许多个候选模型，按优先级、健康状态和能力匹配选择。故障只在同一角色内切换，不跨角色静默降级。每次任务保存实际使用的模型、策略、编译器和计划版本快照。

首期建议默认路由：

```text
vision_analysis  GPT-5.6 或后台配置的同类多模态模型
edit_planning    GPT-5.6 或后台配置的同类结构化规划模型
generation       gpt-image-2.5 主候选，nano banana 2 作为独立候选
quality_check    后台配置的视觉验收模型
```

## 商品保真策略

### strict_product

默认电商策略，要求可信商品主体 mask。商品核心区强保护，背景和融合光晕区允许生成。无法建立可信 mask 时停止严格流程，不静默降级。

### integrated_scene

允许模型重新融合商品边缘、反射和光影，保留商品身份和主要结构，但不承诺商品核心像素级不变。后续由用户或后台显式选择。

### creative_variation

允许商品外观或构图产生更大变化，用于创意探索，不承诺严格商品保真。

## 两条首期工作流

### product_to_scene

输入一张商品主参考图和可选场景参考图。白底背景默认可替换，原有阴影作为姿态和接触面线索，默认重新生成适配新环境的阴影和反射。

商品图决定“是什么商品”；场景图决定“放在哪里、以什么视觉方式呈现”。两者冲突时优先保护商品主参考图。

### local_edit

首期只支持背景、环境、场景道具、光线和阴影修改。系统自动定位唯一编辑目标并生成 mask；多个候选目标时只追问一个问题；用户手动编辑区域优先。

商品颜色、材质、结构和包装文字修改进入后续阶段，必须拥有独立的商品核心验收规则。

## 连续编辑

连续编辑默认以最近成功结果作为当前场景基线，以最初商品图作为原始商品锚点。每轮只记录本轮 `delta`，不无限拼接历史 prompt。

用户明确选择历史结果时创建编辑分支，不覆盖其他结果。新上传商品图时建立新商品锚点；新场景参考图只改变场景参考，不改变商品锚点。

## 失败与回退

- 商品角色识别不确定：只追问一个问题，不猜测。
- 编辑目标有多个候选：只追问一个问题，不扩大 mask。
- 商品 mask 不可信：停止 `strict_product`，给出重新上传或手动标记建议。
- 视觉分析失败：同角色切换候选模型，全部失败则任务待复核。
- 规划失败：不向图片模型发送未验证的 prompt；可回退现有旧流程，但不得伪装成严格商品生成。
- 图片生成失败：沿用现有任务幂等、恢复和候选渠道机制。
- 商品核心验收失败：结果不可判定为成功；自动修复不在首期默认范围内。

## 用户可见状态

内部阶段映射为简短状态：

```text
正在识别商品
正在规划场景
正在生成图片
正在检查商品细节
已完成 / 需要调整
```

用户不看到模型名称、内部 prompt、EditPlan、选择理由和验收细节。

## 验收门禁

每个阶段使用真实家居商品黄金回归集，并执行自动检查和业务人工复核双门禁。

自动检查至少覆盖：

- 输入和结果媒体可读取；
- 商品 mask 覆盖率和编辑区域合法；
- 未编辑区域保护结果可计算；
- 结果资产和父子关系正确保存；
- 实际模型和计划快照完整。

人工检查至少覆盖：

- 商品身份、轮廓、颜色、材质和比例；
- Logo 和包装文字；
- 用户一句话是否完成；
- 欧美家居场景是否自然且适合电商；
- 场景参考图的空间、风格、光线和构图是否被正确借鉴。

商品核心失败直接拦截，不能由场景美观度抵消。

## 发布 SOP

每个阶段必须依次通过：

```text
旧流程基线
  ↓
影子规划，不改变用户结果
  ↓
内部账号启用
  ↓
小比例灰度
  ↓
业务人工复核通过
  ↓
默认启用
```

任何阶段都保留旧流程回退开关。新策略默认不影响 Canvas、短剧和其他未纳入本 SOP 的入口。

## 阶段路线

1. 基线观测与内部快照。
2. `EcommerceEditPlan` 和旧流程兼容编译器。
3. 商品/场景素材角色识别。
4. GPT-5.6 视觉分析和编辑规划。
5. `product_to_scene` 严格商品场景 MVP。
6. `local_edit` 背景、道具、光影局部修改。
7. 连续编辑、双基线和编辑分支。
8. image2.5/nano banana 2 专用编译器和同角色路由。
9. 视觉验收、策略灰度和后台只读状态。
10. 商品颜色、材质和结构编辑的独立设计与验收。

## 非目标与安全边界

- 不用模型名称替代业务能力定义。
- 不让用户承担内部规划和 mask 选择的复杂性。
- 不把未验证的模型能力写成后台可用能力。
- 不把内部计划写入用户公开消息。
- 不在首期为了产出结果而静默降低商品保真策略。
- 不因为连续编辑而覆盖历史结果或丢失原始商品锚点。
